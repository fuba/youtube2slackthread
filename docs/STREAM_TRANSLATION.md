# 翻訳と無音後の意味的な区切り

Issue #4 の実装。既定の ASR は Whisper のまま維持する。翻訳と意味的な終端判定は
明示設定で有効にする。設定の追加例は `config-example.yaml` を参照。
既存の `.env`、`config.yaml`、データベース、Compose、実行中サービスは変更しない。

## 設定

`translation.target_language` に `ja` などの言語コードを指定し、`base_url` と
`model` を設定すると、原文と訳文を同じ連番の Slack メッセージに投稿する。
翻訳を無効にした場合は原文だけを投稿する。

翻訳と意味判定のサービスは `/chat/completions` を提供し、system/user メッセージ、
`max_tokens`、`finish_reason` に対応している必要がある。`base_url` は `/v1` までを含む。
モデル固有の翻訳テンプレートを必要とするサービスは、この汎用アダプターの対象外。
翻訳モデルを自動選定・置換することはしない。

`segmentation.semantic: true` を指定すると、250 ms の無音後に一度だけ認識し、
認識文脈が文またはまとまった節として完結しているかを設定したモデルで判定する。
判定が否定なら音声を保持し、次の発話と無音を待つ。肯定なら同じ認識結果を再利用する。
追加音声が入った場合は再認識する。連続発話中に毎秒認識する処理はない。

意味判定が無効・否定・失敗でも、1.5 秒の無音または最大 12 秒で確定する。
最大長は VAD フレーム単位で切り下げ、音声サンプル数から測る。処理待ち時間や
録画の読み込み速度には依存しない。短い発話や句読点のない末尾も捨てない。
最大長・入力終了・停止時の断片に句読点や欠けた文を付け足さない。
翻訳への指示でも未完文の補完を禁じるが、モデルが守るかどうかは別途品質評価が必要。

強制分割では音声を重複させず、連続するサンプルを別々に処理する。
文字列一致による重複除去は行わない。同じ発言の繰り返しを消さないためである。
切断位置をまたぐ単語の認識品質は評価が必要であり、欠落ゼロを保証するものではない。

`asr.backend: compatible` と `base_url`、`model` を指定すると、既存のローカル ASR
選択を `/audio/transcriptions` の multipart API に切り替えられる。
Qwen3-ASR 0.6B / 1.7B は、対応サーバーで提供されるモデル ID を指定して比較する。
API 形式の参考: [vLLM の Qwen3-ASR 手順](https://github.com/vllm-project/recipes/blob/main/Qwen/Qwen3-ASR.md)。
サーバーの構築・モデル取得・量子化の選択はこの変更に含まない。
個人の OpenAI API を選択した利用者の設定は維持し、既存のローカル ASR 利用制限も適用する。

各サービスの `api_key_env` は、そのサービス専用の環境変数名を指定する。
キーを YAML に直接記載したり、Slack の利用者入力から URL を設定したりしない。
個人の OpenAI キーや Slack トークンを推論サービス用に流用しない。
既存の配備環境では、必要な変数をサービスへ渡す設定を別途用意する。

## 失敗と終了

HTTP 成功でも、空出力、拒否、出力上限、不正な JSON、未完了の生成は成功としない。
翻訳に失敗した区間は原文・連番・安全なエラーコードを投稿し、訳文を成功扱いしない。
終端判定失敗は長い無音・最大長へフォールバックし、失敗件数を残す。
どちらもストリーム終了時にエラーとして上位へ伝える。推論の暗黙の再試行や
上限引き上げは行わない。

ASR・FFmpeg・Slack 投稿の失敗も上位へ伝える。Slack の応答が不明な場合に
同じメッセージを自動再送しない。手動の `retry` は従来どおり動画全体の再実行であり、
再起動をまたぐ投稿済み位置の永続化や exactly-once 配信は実装していない。

FFmpeg の出力はヘッダーのない PCM16 として扱い、プロセス終了後もパイプに残った
音声を読み取る。停止時の最終確定と一時ファイルの削除は、音声を処理するスレッドだけが
行う。推論が停止待ちの上限を超えた場合は停止完了を報告しない。
推論処理は直列で、処理中は入力パイプのバックプレッシャーが働く。モデルが遅いと
ライブ入力に遅れる可能性があり、低遅延・コスト・認識精度の改善は未認定。

## 再評価

参考レポートは別システムの結果であり、このプロジェクトの性能値として扱わない。
今回の実装は既存の WebRTC VAD（利用不可時はエネルギー検出）と汎用の意味判定 API を使う。
Silero / LiveKit モデル自体の組み込みや、その構成との品質同等性は実装・検証していない。
それらを無条件に導入せず、まず ASR・意味判定・翻訳を独立して比較できる接続口を用意した。

同じローカルの 16 kHz / mono / PCM16 WAV を `scripts/evaluate_stream.py` に渡すと、
Slack へ送信せず本番の区切り・ASR・翻訳処理を実行できる。
本番用の資格情報や Cookie DB を使わない評価用設定・環境を用意すること。
設定した推論サービスには音声・原文が送られる。

```sh
python scripts/evaluate_stream.py recording.wav --config baseline.yaml --user-id EVALUATOR --output baseline.jsonl
python scripts/evaluate_stream.py recording.wav --config candidate.yaml --user-id EVALUATOR --output candidate.jsonl
python scripts/evaluate_stream.py recording.wav --config candidate.yaml --user-id EVALUATOR --output realtime.jsonl --realtime
```

既存のアプリ実行環境内で実行する。出力ファイルは新規作成のみ、権限 0600 とし、
原文・訳文・エラー・音声内の開始終了秒・確定理由を保存するため非公開で管理する。
末尾の summary には ASR 要求数・処理時間・強制分割数・投稿相当の件数・失敗件数を残す。
失敗時は非ゼロ終了する。実時間再生時だけ音声区間末尾からコールバックまでの時間を記録する。
これは Slack API の待ち時間を含まず、実際の投稿遅延ではない。

1. Whisper のモデル・VAD・最大長を固定した条件を基準にする。
2. ASR のモデルだけを変え、0.6B / 1.7B を同じ音声で比較する。
3. ASR と最大長を固定し、意味判定だけを切り替える。
4. 翻訳の比較では保存した同じ原文区間を用い、モデルと区切りを同時に変えない。
5. 原音に基づく人手の正解原稿・訳で、数字・固有名詞・否定・欠落・未完文の補完を点検する。
6. 実サービスで発話から Slack 投稿までの遅延、重複、取りこぼしを別途測定する。

一致率・処理時間だけで品質を認定しない。今回、同一 YouTube 音声と人手正解による
モデル比較および実 Slack 投稿遅延の測定は行っていない。

## 回帰テスト

短い発話、無音、連続発話、意味判定の否定と失敗、最大長、末尾端数、入力異常、
上流失敗、翻訳の空出力・上限、原文とエラーの対応、HTTP 通信をテストする。
既存テストの一部はワークスペース対応前の引数・スキーマを期待していたため、
現行の `team_id` と複合インデックスを確認するように更新した。認証・DB の実装は変更しない。
